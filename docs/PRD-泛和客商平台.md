## 1. 背景介绍

### 1.1 业务背景

集团业务板块较多，涉及货代、船员派遣、船舶管理、船代、租船订舱、数字化服务等。客户群体高度集中在航运产业链内，但客户信息、联系人资源、需求线索和客情记录分散在不同团队或个人手中，缺少统一沉淀与跨板块协同机制。

因此需要建设一个轻量级 CRM 工具，先以移动端/微信小程序形态服务集团内部使用，让各板块能够共享客户主数据、同步客户背景信息、录入和跟进需求，并通过统计能力辅助管理层了解客户资源和业务线索分布。

### 1.2 业务场景

| 场景/业务模式 | 业务价值 |
| --- | --- |
| 客户管理 | 建立客户主数据，记录联系人、标签、客情关系、航线、背景补充等信息 |
| 需求管理 | 将原“商机”统一改为“需求”，支持跨业务板块共同跟进需求线索 |
| 标签分流 | 通过省市/国家、行业、航线、其他标签进行客户分层和筛选 |
| 客户背景补充 | 平台用户可持续补充客户诉讼、赖账、经济纠纷等关键信息 |
| 通知协同 | 录入员新增客户后管理员可收到平台通知，后续接入微信通知 |
| 统计分析 | 从客户、需求、录入贡献、重复联系方式等维度辅助管理判断 |

### 1.3 核心问题

1. 客户数据分散，集团层面无法统一查看和复用。
2. 航运业务标签复杂，单纯区域划分不足以支撑筛选和业务分流。
3. 不同业务板块对同一客户的背景认知不一致，缺少可追溯补充记录。
4. 需求线索缺少统一入口和跟进状态，跨团队协作成本较高。
5. 管理员需要掌握录入情况、需求分布和潜在重复联系方式。

### 1.4 本期目标

1. 建立移动端优先的客户与需求信息管理原型。
2. 通过首页先分流再进入详情，降低全量客户直出造成的信息压力。
3. 建立标准标签词典，并支持省市/国家、行业、航线、其他标签管理。
4. 支持客户 Excel 批量导入、导出和模板下载。
5. 建立基础权限体系，区分管理员和录入员能力边界。
6. 建立平台通知中心，为后续微信通知预留业务逻辑。

## 2. 产品概述

### 2.1 产品定位

泛和客商平台是集团内部使用的航运客户管理工作台，用于统一沉淀客户主数据、需求线索、联系人关系、客户标签和背景补充信息。

初期产品形态为移动端 Web 原型，后续以微信小程序为主要使用入口。

### 2.2 服务对象

| 用户类型 | 典型用户 | 核心诉求 |
| --- | --- | --- |
| 管理员 | 集团及各子公司总经理、管理人员 | 查看全量客户和需求，管理账号、标签、统计与关键通知 |
| 录入员 | 各子公司配置的客户/需求录入人员 | 快速录入客户与需求，维护本人负责的信息，查看业务通知 |

### 2.3 产品逻辑

产品采用“首页分流 + 详情沉淀 + 统计复盘”的核心逻辑：

1. 用户登录后进入首页，先看到客户总量、今日新增、省市分布、行业分类和重点客户列表。
2. 用户可通过首页标签、底部导航或搜索进入客户列表和客户详情。
3. 客户详情作为客户主档，沉淀客户基础信息、联系人、需求数量和背景补充记录。
4. 需求页面用于管理客户需求线索，支持跟进状态、@协同和补充信息。
5. 统计页面聚合关键指标，辅助管理员查看需求、录入和重复联系方式。
6. 我的页面承载个人信息、通知、用户管理、标签管理等管理功能。

### 2.5 角色术语

| 角色 | 定义 | 客户/需求权限 | 统计权限 | 管理权限 |
| --- | --- | --- | --- | --- |
| 录入员 | 各子公司配置的录入人员，负责客户建档、需求录入等工作 | 可新增客户和需求；可维护本人录入的信息；普通用户不展示删除入口 | 默认无完整统计管理权限，具体可按组织策略开放 | 无创建账号、用户管理、标签管理权限 |
| 管理员 | 集团或各子公司总经理/管理人员 | 可查看和管理全量客户、需求；可执行删除操作 | 可查看统计页面和详细统计列表 | 可创建账号、管理用户、管理标签词典 |

### 2.6 业务术语

| 术语 | 说明 |
| --- | --- |
| 客户 | 航运产业链内的公司、组织或潜在合作方 |
| 需求 | 原“商机”，指客户或潜在客户产生的业务需求、合作线索或待跟进事项 |
| 标签词典 | 平台统一维护的标准标签集合，包括省市/国家、行业标签、航线标签、其他标签 |
| 省市/国家标签 | 用于客户主要办公地或业务所在地筛选；国内按省/市二级结构，国外可作为国家标签 |
| 行业标签 | 航运相关行业分类，可支持多级标签，例如船舶服务、货代服务、船管等 |
| 航线标签 | 客户涉及的航线，例如地中海航线、南美航线、中东航线、非洲航线等 |
| 其他标签 | 用户自定义标签，例如散货船东、特种箱船东等，不进入级联筛选，主要通过搜索命中 |
| 背景信息补充 | 用户在客户详情中追加的类评论记录，用于补充诉讼、赖账、经济纠纷等关键信息 |
| @提醒 | 在需求描述或补充信息中通过 @ 平台用户形成协同提醒，后续可联动微信通知 |

### 2.7 范围说明

当前原型主要验证移动端交互、页面结构和业务字段。部分数据为 mock 数据或浏览器本地存储，正式版本需要接入后端接口、权限服务、消息服务、微信通知能力和数据持久化。

### 3.2 页面与功能明细

#### 3.2.1 登录页

> 截图占位：登录页，展示顶部船舶背景图、登录卡片、账号密码输入框和登录按钮。

**页面目标**

用户通过账号密码登录系统，系统根据用户角色进入对应权限视图。

**功能要求**

1. 支持用户名、密码输入。
2. 密码输入框支持显隐切换。
3. 登录成功后进入首页。
4. 登录失败时展示明确错误提示。
5. 页面使用顶部航运背景图，右侧船舶元素应在移动端可见，整体重心居中，避免底部大面积空白。

**校验规则**

| 字段 | 规则 |
| --- | --- |
| 用户名 | 必填 |
| 密码 | 必填；正式环境需支持强密码策略 |

#### 3.2.2 首页

> 截图占位：首页，展示“泛和客商平台 / 航运客户管理工作台”、今日概览、省市分布、行业分类、客户统计列表。

**页面目标**

首页承担“先分流再进入”的入口作用，不直接堆叠全量客户列表，而是先通过核心指标和主要标签帮助用户判断进入方向。

**展示内容**

1. 今日概览：客户总数、今日新增。
2. 省市分布：展示主要省市/国家及客户数量，标签横向滑动。
3. 行业分类：展示主要行业标签及客户数量，支持条形进度形式。
4. 客户统计列表：展示需求数量较多的客户，按需求数量降序排列。

**交互要求**

1. 点击省市/国家标签，进入客户列表并带入对应筛选条件。
2. 点击行业标签，进入客户列表并带入对应筛选条件。
3. 点击客户统计列表项，进入客户详情。
4. 首页顶部背景和其他主页面保持一致，控制高度，避免占用过多首屏空间。

#### 3.2.3 客户列表

> 截图占位：客户列表页，展示顶部背景、搜索框、筛选下拉、客户卡片、右下角新增和导入导出浮动按钮。

**页面目标**

为用户提供客户查找、筛选、查看和快速操作入口。

**功能要求**

1. 搜索框支持按公司名称、地址、联系人、电话、邮箱、行业标签、航线标签、其他标签检索。
2. 搜索框点击后展示近期搜索记录。
3. 筛选项包括省市/国家、行业标签、航线标签。
4. 省市/国家和行业使用级联选择逻辑，适配移动端操作。
5. 航线标签为非必填标签，筛选时作为单独筛选维度。
6. 其他标签不进入下拉筛选，通过搜索框关键字命中。
7. 客户卡片展示公司名称、所在地、联系人数量、需求数量、录入人、联系人、电话、邮箱、标签。
8. 行业标签、航线标签、其他标签在同一区域展示，但使用克制的不同色系区分。
9. 管理员可见删除按钮；录入员不可见删除按钮。
10. 右下角提供新增客户、Excel 导入/导出等浮动操作，按钮尺寸适配移动端，不遮挡主要内容。

**客户卡片操作**

| 操作 | 说明 | 权限 |
| --- | --- | --- |
| 查看详情 | 点击卡片主体进入客户详情 | 管理员、录入员 |
| 编辑 | 编辑客户信息 | 管理员、信息负责人/录入员 |
| 添加需求 | 以当前客户为上下文新增需求 | 管理员、录入员 |
| 删除 | 删除客户 | 仅管理员 |
| 收藏 | 当前原型展示收藏入口，正式版可按业务决定是否保留 |

#### 3.2.4 新增/编辑客户

> 截图占位：新增/编辑客户页，展示客户基础信息、标签选择、联系人维护和保存按钮。

**字段要求**

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| 客户名称 | 文本 | 是 | 公司或组织名称 |
| 主要办公地 | 级联选择 | 是 | 国内按省/市选择，国外按国家选择 |
| 统一社会信用代码 | 文本 | 条件必填 | 当主要办公地为国内时必填，用于客户唯一性识别 |
| 行业标签 | 多选/级联 | 建议必填 | 使用标准行业标签词典，支持航运相关行业 |
| 航线标签 | 多选 | 否 | 例如地中海航线、南美航线、中东航线、非洲航线 |
| 其他标签 | 自定义多选 | 否 | 用户可新增自定义标签，归类为“其他标签” |
| 注册资金 | 文本/数字 | 否 | 人工维护，当前不对接企查查 |
| 地址 | 文本 | 否 | 支持客户列表按地址关键字搜索 |
| 电话 | 文本 | 否 | 客户公司电话 |
| 邮箱 | 文本 | 否 | 客户公司邮箱 |
| 客户描述 | 多行文本 | 否 | 补充客户基础说明 |
| 联系人 | 列表 | 建议至少 1 个 | 包含姓名、电话、职位、客情关系等 |

**联系人字段**

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 姓名 | 是 | 联系人姓名 |
| 电话 | 是 | 联系人电话 |
| 职位 | 否 | 联系人在客户公司的职位 |
| 邮箱 | 否 | 联系人邮箱 |
| 客情关系 | 是 | 枚举值建议：认识、可约局、可支持 |

**标签要求**

1. 行业标签使用标准词典，包含船管、船代、货代、租船订舱、港口服务、报关报检、船员派遣、船舶维修、物流企业、软件与数字化、人工智能、国际贸易等。
2. 航线标签作为客户业务范围补充，支持多选，不强制填写。
3. 其他标签支持自定义输入，例如散货船东、特种箱船东、危险品运输、冷链物流、滚装船资源等。
4. 自定义其他标签可通过搜索框检索，不作为顶部下拉筛选项。

#### 3.2.5 客户详情

> 截图占位：客户详情页，顶部固定返回，展示客户主档、联系人、需求、背景信息补充列表。

**页面目标**

客户详情是客户主数据沉淀页面，集中展示客户基本信息、联系人、需求数量和背景风险信息。

**功能要求**

1. 顶部左侧固定返回操作，和系统其他详情页一致。
2. 展示客户名称、所在地、标签、联系人、电话、邮箱、录入人等信息。
3. 展示客户关联需求列表或需求数量入口。
4. 支持添加背景信息补充，入口放在“背景信息补充”标题旁边。
5. 点击添加按钮后弹出表单弹窗，不直接在页面底部展开表单。
6. 补充信息以类评论形式按时间倒序展示。

**背景信息补充字段**

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 信息类型 | 是 | 诉讼、赖账、经济纠纷、信用风险、关系补充、其他 |
| 补充内容 | 是 | 用户填写的详细信息 |
| 补充人 | 系统生成 | 当前登录用户 |

### 3.5 非功能需求

#### 安全需求

1. 正式环境必须使用 HTTPS。
2. 账号密码需支持强密码校验。
3. 登录态需设置有效期和刷新机制。
4. 敏感数据导出需记录操作日志。
5. 管理员权限接口需要后端校验，不能只依赖前端隐藏按钮。

#### 性能需求

1. 移动端首屏加载需控制资源体积。
2. 客户列表、需求列表应支持分页或滚动加载。
3. 搜索和筛选在数据量增加后应由后端接口支持。
4. Excel 导入需异步处理，避免阻塞页面。

#### 兼容需求

1. 优先适配微信小程序 WebView 或小程序原生实现。
2. 移动端设计宽度以主流手机屏幕为基准。
3. 页面需适配 iOS 和 Android 常见浏览器。

#### 可维护需求

1. 标签词典应由后台统一管理，不建议硬编码在前端。
2. 统计口径需要接口层统一定义。
3. 通知事件建议通过统一消息服务生成。

## 4. 交互与视觉要求

### 4.1 移动端导航

1. 底部导航包含：首页、客户、需求、统计、我的。
2. 当前选中项需有清晰高亮状态。
3. 详情页、管理页、统计详细页顶部左侧固定返回，用户下滑后仍可快速返回。
4. 主页面顶部背景图保持统一，图片位置和高度一致。

### 4.2 页面风格

1. 整体风格应简约、大气、企业内部系统感，避免 ToC 式炫酷效果。
2. 色彩以稳重蓝为主，辅助色低饱和处理。
3. 行业、航线、其他标签可使用不同色系，但应降低亮度和饱和度，避免突兀。
4. 电话、邮箱、编辑等操作按钮颜色需克制，与系统主色协调。
5. 卡片间距、按钮高度、标签尺寸需要适合移动端，一屏内尽量展示更多有效信息。

### 4.3 表单交互

1. 长表单应分组展示，减少用户理解成本。
2. 补充信息类表单使用弹窗，不直接在详情底部展开。
3. @输入需要在输入 `@` 后展示用户下拉选择。
4. 删除操作需二次确认。

## 5. 通知与外部集成

### 5.1 平台通知

当前阶段平台内置通知中心，保留通知历史。管理员可查看录入员新增客户、@提醒、客户背景补充等消息。

### 5.2 微信通知

后续小程序版本优先接入微信通知能力。建议将通知事件抽象为统一消息事件，再分别投递到平台通知中心和微信消息。

### 5.3 企业数据接口

当前注册资金、地址、统一社会信用代码等字段由人工维护，暂不接入企查查等第三方数据。后续可按业务需求评估企业工商数据接口。

## 6. 数据导入导出

1. 客户导入导出作为客户列表的辅助操作，不占据顶部主空间。
2. 导入模板需要固定字段和示例值。
3. 导入过程需支持字段校验、失败行提示和重复客户识别。
4. 导出需支持导出当前筛选结果或全量客户，具体权限由管理员配置。
5. 涉及敏感数据的导出需记录操作人和导出时间。
